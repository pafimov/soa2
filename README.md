# Marketplace

ДЗ №2. Один сервис на Go: товары, заказы, промокоды, авторизация. База — PostgreSQL, миграции — Flyway. HTTP-хэндлеры и DTO генерируются из OpenAPI через oapi-codegen. Валидация запросов — kin-openapi и проверка денежных значений в копейках.

## Запуск

Нужны Docker и Docker Compose. Для первой сборки нужен доступ к реестру образов и Go-модулям.

```sh
cp .env.example .env
docker compose up --build -d app
```

API слушает `http://localhost:8080`. Сначала поднимается PostgreSQL, затем Flyway применяет миграции, после него запускается приложение. При сборке генерируется `internal/api/api.gen.go`.

```sh
docker compose logs -f app
```

В `.env.example` лежат только локальные настройки. Перед внешним размещением нужно заменить пароли и JWT-секреты, а HTTP закрыть HTTPS-прокси. База и API в compose опубликованы только на `127.0.0.1`.

## Быстрая проверка

После запуска приложения:

```sh
python3 scripts/smoke.py
```

Скрипт создаёт продавца и покупателя, проверяет запрет создания товара покупателем, создаёт товар и промокод, оформляет и обновляет заказ, отменяет его, архивирует товар и обновляет токены. Для каждого запуска используются новые email и промокод. Тестовые записи остаются в базе.

Для другого адреса:

```sh
python3 scripts/smoke.py --url http://localhost:8081
```

Пример отдельного запроса:

```sh
curl -i -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@example.test","password":"local-admin-password-123"}'
```

Из ответа нужен `access_token`. Дальше он передаётся как `Authorization: Bearer <access_token>`. Спецификация со всеми телами запросов находится в `api/openapi.yaml`; её можно открыть в Swagger Editor.

## Сборка и тесты

Локально нужны Go 1.23+ и make.

```sh
make generate
make build
make unit
make test
make integration
```

`make generate` — только кодогенерация. Версия генератора закреплена в Makefile. `make build` сначала генерирует код, выполняет `go mod tidy`, затем собирает бинарник. Сгенерированные файлы добавлены в `.gitignore`; вручную их менять не нужно. `internal/money.Amount` — скалярный тип суммы, указанный в OpenAPI через `x-go-type`.

`make unit` запускает тесты денежных вычислений и состояний без внешних модулей. `make test` запускает также HTTP-тесты валидации, JWT, логирования и матрицы ролей. Без `TEST_DATABASE_URL` интеграционные тесты пропускаются.

`make integration` поднимает PostgreSQL, применяет Flyway к отдельной базе `marketplace_test` и запускает все Go-тесты в контейнере с `-race`. Проверяются откаты, порядок бизнес-ошибок, снимки цен, промокоды, ограничения частоты, чужие заказы и конкурентные запросы. Ответы обычных интеграционных сценариев дополнительно проверяются по OpenAPI. Тесты не очищают таблицы и создают собственные данные.

Сборка использует Go 1.23.6 на Alpine; зависимости и генератор кешируются отдельными слоями. Финальный контейнер содержит статический бинарник и CA-сертификаты. GCC и заголовки C устанавливаются только в тестовый образ для `-race`.

Для запуска бинарника на хосте с базой из compose:

```sh
docker compose up -d db
docker compose run --rm migrate
set -a
. ./.env
set +a
make run
```

База `marketplace_test` создаётся init-скриптом при первом создании тома PostgreSQL. Для уже существующего тома без этой базы:

```sh
docker compose exec db createdb -U marketplace marketplace_test
```

Остановка без удаления данных — `docker compose down`. Команда `docker compose down -v` удаляет том и все данные, поэтому для обычной остановки она не нужна.

## Настройки и роли

`ORDER_LIMIT_MINUTES` — интервал между успешными операциями одного типа, по умолчанию 5 минут. `CREATE_ORDER` и `UPDATE_ORDER` учитываются отдельно. Значение 0 отключает задержку, но не проверку активного заказа.

При регистрации можно выбрать `USER` или `SELLER`; без роли создаётся `USER`. Публично зарегистрировать `ADMIN` нельзя. Первый администратор создаётся из `ADMIN_EMAIL` и `ADMIN_PASSWORD`. Если оба значения пустые, этот шаг пропускается. Уже существующему пользователю права не повышаются, пароль существующего администратора при перезапуске не меняется.

Access token действует 15 минут, refresh — 14 дней. Для них используются разные секреты. Refresh одноразовый: после успешного обмена старый токен больше не принимается, возвращается новая пара. В БД хранится идентификатор refresh, а не сам токен.

## Что где лежит

```text
api/                  OpenAPI и конфиг генератора
cmd/server/           запуск сервиса
internal/app/         HTTP, валидация, SQL, бизнес-логика и тесты
internal/money/       денежный тип
internal/rules/       скидки и переходы состояний
internal/api/         сюда генерируется код при сборке
db/migration/         миграции Flyway
scripts/smoke.py       проверка запущенного API
```

## Принятые решения

В условии есть места, для которых пришлось выбрать конкретное поведение.

**Процентная скидка.** Фразу «в ином случае цена 100%» трактую так: процент больше 70 даёт нулевую скидку, а не скидку 70%. Например, для суммы 1000 и процента 80 итог будет 1000. Промокод при этом считается использованным. При допустимом проценте скидка округляется до копейки, но результат не может превысить 70% исходной суммы. Фиксированная скидка ограничивается всей суммой заказа.

**Повторная проверка промокода.** При обновлении заказа его собственное использование не считается чужим занятым местом. Иначе промокод с `max_uses=1` нельзя было бы сохранить даже в том же заказе. Повторного инкремента нет. Если сумма стала меньше минимума, промокод снимается и использование возвращается. Если он истёк или отключён, обновление завершается `PROMO_CODE_INVALID` и полностью откатывается.

**Снимки цен.** При изменении количества старой позиции сохраняется её `price_at_order`. Для нового товара берётся текущая цена. Если товар удалён из заказа и позже добавлен заново, это уже новая позиция с новой ценой. Одинаковый `product_id` нельзя передать дважды; это отражено в OpenAPI расширением `x-unique-product-ids`.

**Смена состояний.** В задании есть цепочка состояний, но нет метода продвижения по ней. Добавлен `POST /orders/{id}/status`, только для `ADMIN`, с телом `{"status":"PAYMENT_PENDING"}`. Он разрешает один шаг вперёд. Отмена остаётся отдельным `/cancel` и возможна из `CREATED` и `PAYMENT_PENDING`.

**Права администратора.** `ADMIN` может читать, менять и отменять чужие заказы согласно матрице. Лимит обновлений считается для того, кто делает запрос. При создании товара администратор может указать `seller_id`; продавец — только свой ID. Через обновление товара сменить владельца нельзя.

**Товары и суммы.** `PUT /products/{id}` — полная замена изменяемых полей. Отсутствующее или `null`-описание очищается. `stock` означает свободный остаток без резерва. Архивные товары остаются видны в каталоге; убрать их можно фильтром `status=ACTIVE`. Повторное удаление уже архивного товара возвращает 204. Денежные значения передаются числами, например `199.90`, а не строками. Максимум суммы соответствует `DECIMAL(12,2)`; больший заказ отклоняется с `ORDER_AMOUNT_EXCEEDED`.

## Транзакции и логи

Создание, изменение и отмена заказа выполняются целиком в транзакции. Строки товаров блокируются в порядке ID, строка промокода тоже блокируется. Проверки частоты и активного заказа сериализуются блокировкой строки пользователя. Дополнительно есть уникальный частичный индекс на один активный заказ пользователя. `created_at` и `updated_at` выставляет база, изменение `updated_at` — триггером. Допустимые переходы состояния проверяются и в Go, и триггером.

Логи запросов идут в stdout в JSON. В ответе возвращается новый `X-Request-Id`, он же попадает в лог. Для `POST`, `PUT`, `DELETE` пишется тело, пароли и токены заменяются на `***`. Некорректный JSON целиком в лог не попадает, чтобы случайно не записать пароль из сломанного запроса.
